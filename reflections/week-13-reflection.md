## Part 2 — A Specific Bug

**2a. Describe the hardest bug you fixed this semester. Not the most recent one — the one that took the longest or cost you the most confusion. What was the symptom? What did you think the problem was at first? What was it actually? How did you find it?**

- The JSON serialization mismatch on the login request. The symptom was the server returning 400 on every login attempt even with correct credentials. I assumed it was a token or header issue at first and spent time tracing `AuthInterceptor`. The actual problem was that the JSON keys in the request body didn't match what the backend expected. The field names in the Kotlin data class were slightly off and `kotlinx.serialization` was serializing them as-is without any `@SerialName` mapping. I only found it by turning on the OkHttp logging interceptor and reading the actual request body that went over the wire.

---

**2b. Copy and paste the specific lines of code you changed to fix it. (This can be a before/after comparison, a diff, or just the relevant snippet.) Explain in plain English what the fix does and why it works.**

> Before:
> ```kotlin
> @Serializable
> data class LoginRequest(val email: String, val password: String)
> ```
> After:
> ```kotlin
> @Serializable
> data class LoginRequest(
>     @SerialName("email") val email: String,
>     @SerialName("password") val password: String
> )
> ```
> The `@SerialName` annotation tells `kotlinx.serialization` exactly what key to use in the JSON output regardless of what the Kotlin property is named. Without it the serializer uses the property name directly, and if that doesn't match the backend contract exactly the server rejects the request.

## Part 3 — What You Actually Learned

**3a. Pick the concept from this semester that took the longest to actually understand — not just to implement, but to understand. Describe what you thought it was before you understood it, what changed, and how you would explain it now to a student who was exactly where you were at the start of the semester.**

- State management in the ViewModel layer. Early on I thought "state" just meant storing values, have a variable, update it, done. What I didn't understand was why each failure mode needed its own sealed class case. In week 11 building `ReviewResult` with `Success`, `AlreadyReviewed`, `NotFound`, `NetworkError`, and `UnknownError` made it actually click. The compiler forces you to handle every case in a `when` expression, which meant I had to think about what the screen does for a 409 conflict versus a network timeout versus a 404, separately and intentionally. Before, I was collapsing all of that into a generic error string and losing the distinction. Now I'd explain it this way: a sealed class is a contract that says "these are all the things that can happen, and you don't get to ignore any of them."

Are you still confused about it? If not, when and how did it click? If you still are, say so honestly and describe what the sticking point is.**

- Week 3 I wrote that I was confused about where the token gets stored after login, how it gets attached to future requests, and how the app recovers if the token expires. By week 6 that had fully clicked. `DefaultSessionRepository` persists the token to DataStore. `AuthInterceptor` reads it lazily per-request using `runBlocking` on the OkHttp thread. The startup decision between login screen and main content comes from checking whether `getAccessToken()` returns null. Seeing `AuthInterceptor` finally made the pieces connect: it's not that the ViewModel or repository "knows" about the token, the interceptor just silently attaches it to every outgoing request.

## Part 4 — Your Bonus Feature

**4a. Describe your bonus feature in one paragraph as if you were explaining it to someone who has never used an app before. What does it do? Why would a user want it?**

- The Write Review feature lets you leave a star rating and a written review for any movie, book, or show in the app. You pick 1 to 5 stars, type whatever you want to say (up to 500 characters), and optionally share it to the activity feed so your connections can see it. If you already wrote a review for something, the app shows you your existing one with Edit and Delete buttons so you're not stuck with your first take. A user would want it because tracking what you watched is more useful when you can actually record what you thought of it.

---

**4b. What was the technically hardest part of building it? Name a specific function, flow, or data structure that gave you trouble, and explain what the problem was.**

- The `loadForEdit()` flow in `WriteReviewViewModel`. The screen receives a `reviewId` as a nav argument, but loading for edit meant calling `getReviews(mediaId)`, getting back the full list, and then finding the matching review by id to pre-populate the form. The tricky part was the guard `if (editingReviewId == reviewId) return`. Without it, any recomposition of the screen could call `loadForEdit()` again and reset the user's in-progress edits mid-typing back to the original fetched values.

**4c. Your bonus feature has tests. Open the test file and paste the test you think is most valuable — the one that would catch the most important failure. Explain what it proves and what it does not prove.**

- A test does exist. The file `LibraryViewModelRollbackTest.kt` contains two unit tests for the optimistic-remove feature. The most valuable one is `removeItem rolls back when network call fails`.
>
> What the test does:
> - Seeds the list with two `LibraryItem` stubs
> - Mocks `removeFromLibrary` to throw an `IOException`
> - Calls `removeItem(1)` and confirms the item disappears optimistically
> - Advances the coroutine dispatcher with `advanceUntilIdle()` so the network call runs and fails
> - Asserts item 1 is restored, the list count returns to 2, and `errorMessage` is set to "Couldn't remove item. Try again."
>
> What it proves:
> - The optimistic-delete path reverts state on network failure
> - The error message surfaces correctly — both things that would silently break if someone dropped the `catch` block or forgot to re-append `backup`
>
> What it does not prove:
> - The rollback logic is inlined in the test class rather than the real `LibraryViewModel`, so a ViewModel refactor that doesn't copy the same structure would not be caught
> - Concurrent removals (two items removed before the first failure resolves) are not covered
> - The case where `backup` is null because the item was already absent is not tested

**5b. A friend tells you they want to learn Android development. Based specifically on your experience this semester — not what you've read, what you lived — what is the one thing you would tell them to understand before they write a single line of code?**

- Understand the data flow before you write a single screen. The layering of Retrofit service, repository, ViewModel, and composable looks like overhead at first, but every weird bug I spent the most time on came from not respecting it: putting network logic in a composable, updating state directly instead of going through the ViewModel, collapsing all error cases into one string. Once that separation is instinctive the rest follows. But if you try to learn Compose and coroutines and the architecture all at once without understanding why they're structured that way, you end up with working code that you can't debug.
